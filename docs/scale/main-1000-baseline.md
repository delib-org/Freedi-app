## How to read these numbers

**measured** means counted during the run. **derived** means a measured number multiplied up, and the note says by what.

- **Function reads and writes (measured).** `scripts/scale/trace-shim.cjs` is preloaded into every functions emulator worker. It wraps the Admin SDK's query, document-read and commit calls and logs documents per invocation, so "docs read per rating" and "question doc writes" are exact counts, with no change to application code. A query returning nothing counts as one read, as Firestore bills it. Retried transactions count again, as Firestore bills them.
- **Client downloads (measured on a sample).** 10 real client-SDK connections sign in anonymously through the Auth emulator and run the app's own query shapes, under the real security rules. Documents counted are `docChanges()` per listener, or the result size of one-shot reads. Sources: `useStatementListeners`, `listenToSubStatements` (head start of 10, then newest 30), `ListenToOnlineUsers`, `useParticipationStats`.
- **Multiplying up (derived).** Per-participant counts are multiplied by 1,000, and a write's fan-out is writes x listeners. The sample shows each listener receives each write; it does not run 1,000 sockets.
- **Exposure.** The query is real and asked at each simulated arrival; arrival order, 10 ratings each and no scrolling are a model. People who scroll load older answers (`useLazyLoadOptions`), so the model understates reach for those who do.
- **Pacing.** Trigger-firing writes go in batches of 5, waiting for the emulator to go quiet between batches, so a backlog does not swamp the counts. The `rate-simultaneous` phase is the exception: its ratings land at once.
- **Rating model.** Burst raters are returning participants (already counted) who rate one card each, rotating across the newest 30 with mixed values (+1 to -1). The `rate-first-time` phase measures a person's first rating separately, which also moves the evaluator counters. How often a rating changes the top results depends on the rating pattern, so that part of the question-document cost is model-dependent. Ratings on answers outside the newest 30 deliver no answer document to anyone.
- **Seeding** runs with background triggers disabled, then the question's counters are written directly so the burst meets a realistic question. Burst phases run with triggers on, after one warm-up action of each kind whose cost is not counted.

## What this baseline cannot show

- **Billing.** The emulator does not bill. Counts mirror the billing rules, but index-entry reads for aggregations, listener resume costs and offline-cache hits are not modelled.
- **Real concurrency.** Workers on one machine, run 15 at most in the simultaneous phase. No per-document write-rate limits; the emulator's transaction locking is pessimistic, unlike production's optimistic retries. So contention on the question document under real load is not visible here.
- **Cold starts and instance behaviour.** Workers are warmed first and never freeze after returning. So a fire-and-forget write always finishes here, and "credits complete" proves little. What it can show is how many credit writes land after the trigger returned: those are the ones at risk in production. Per-instance caches (the 30 s cache for plan item 3.5) are not exercised.
- **Listeners at full scale.** 10 listeners, not 1,000. Coalescing of snapshots and delivery latency under 1,000 sockets are unknown.
- **Durations** are local and useful only for comparing triggers within one run.
- **Excluded on purpose.** AI, email and Sentry traffic: `functions/.env.local` blanks the keys during the run and turns live synthesis off, so live-synthesis and embedding-generation costs are not included. Push sends are not exercised (seeded subscribers hold no tokens); in-app notification writes are.
- **Not sampled on open.** The four demographic listeners (questions and answers, statement and group) and `listenToInAppNotifications`. On a question with no demographic survey each costs about one read.

Exposure moved too, as a modelled behaviour rather than a cost: above 30 answers the sampler replaces the newest-first feed. Ratings per answer are now even, 30 for the oldest quarter and 30 for the newest (was 23.3 and 61.7), and the most-rated tenth of answers took 10% of the ratings (was 36.4%).

### What these numbers cannot show

- **The dispatcher stays off until a production cutover.** `onStatementWriteDispatch` is deployed but inert until `STATEMENT_DISPATCH_CUTOVER_MS` is set, so a statement write starts 19 functions here (the 18 old triggers plus the idle dispatcher), not the 6 expected after the cutover. Function starts per rating rose from 23.5 to 24 for the same reason. See `statement-dispatch-cutover.md`.
- **Notification writes per new answer did not improve, by design.** Above the large-question threshold the in-app write is kept and instant push and email give way to one daily digest; the emulator has no push tokens and email is off, so only the in-app writes are visible.
- **The emulator does not bill and does not enforce indexes.** Counts mirror the billing rules, but a missing composite index would pass here. `fetchTopAnswers` needs `(parentId, statementType, consensus DESC)`, which exists in `firestore.indexes.json`.
- **Global counters still write three docs per rating.** Lane K moved contention onto shards and a 10-minute sync; the count of `adminStats` writes per rating is the same, and shard contention is not visible on one machine.
- **Sharded and cached numbers are per-worker.** `getAnswerBatch` caches answers per instance for 30 s, so its 158 reads per call are a few cold workers reading all 300 answers, on one machine. Production depends on the number of instances.
- **Ten listeners, not 1,000.** Multiplying up assumes each listener gets every write, as the sample shows; socket coalescing under real load is unknown.
- **The rate phase is a mid-session model.** Burst raters choose from the sampler with half-scaled counts, because at the end of the simulated session all answers are stable and the sampler offers nothing. Without that the answer-window number would be meaningless.

### Failed commits in the after run

`new-answer` shows 3 failed commits: `largeQuestionDigest` uses `create()` on the per-question digest marker, and the warm-up answer had already created it, so those are expected `ALREADY_EXISTS` results. `answer-batch` shows 1: a contended rate-limit reservation, reported as a failed commit by the trace and not an error for the caller.
